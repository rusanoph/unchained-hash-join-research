## Execution

Natural physical planning creates `HashJoinExec` through `HashJoinExecBuilder` with equality expressions, projection, join filter and partition mode. Its build collects the left physical input after any optimizer swap or repartition. Baseline regular joins use `ArrayMap` for eligible dense integers and `JoinHashMapU32/U64` otherwise, with a linked chain from the directory entry into build row IDs. The hash map hashes the build in bounded slices and defers exact candidate-key comparison to the probe. B's regular inner, left, right and full path uses `JoinIndexMap` around a width-selected `JoinHashIndex`. Existence/as-of specifics require inspecting their own execution path. Existence joins can retain the original map path in B. In the regular path B increments `array_map_created_count` when `index.is_dense()`. [Physical planner](https://github.com/apache/datafusion/blob/2f6c665fef63936f08a4aa7a4fb01b87a4d2b009/datafusion/core/src/physical_planner.rs#L1945), [A hash join](https://github.com/apache/datafusion/blob/6a060586ed85d2ff71837b6d818b7eddc075b699/datafusion/physical-plan/src/joins/hash_join/exec.rs), [B hash join](https://github.com/apache/datafusion/blob/2f6c665fef63936f08a4aa7a4fb01b87a4d2b009/datafusion/physical-plan/src/joins/hash_join/exec.rs).

The PR uses dense direct-address slots when a single integral key meets range, density and NULL constraints. The integer SwissTable directory inlines the key for a direct equality comparison. The general SwissTable stores hash and representative build row and checks actual key equality during insertion for compatible hashes. This keeps equal-key groups distinct even after a hash collision. General probing prepares batch lookups and validates candidates against representatives. The hash-based directories reserve and create a `Vec<u64>` for the entire build in addition to validity/hash scratch. Dense construction reads integer keys without this buffer. `u32` IDs cover builds with at most `u32::MAX` rows, and `u64` covers larger builds. [Directory selection and dispatch](https://github.com/apache/datafusion/blob/2f6c665fef63936f08a4aa7a4fb01b87a4d2b009/datafusion/physical-plan/src/joins/join_index/directory.rs).

On first insertion each key gets `MatchHandle::One(row)`. A repeat promotes the entry to `Group(id)`. `MatchedGroupsBuilder` stores first rows, counts and pending `(group,row)` pairs. Its capacity and temporary reservation start at worst case. With `u32` the reservation is approximately 14 bytes per build row, including for unique keys. Final offsets and contiguous row IDs can coexist with this reservation during scatter. The unique probe result can carry matched pairs directly. The grouped probe path stores match handles and bitmaps, then expands groups with `GroupCursor` in bounded batches under `BatchedJoinProcessor`. Residual conditions operate on candidate indices before the Arrow gathers and outer-match bookkeeping. Build allocations are accounted against DataFusion's pool via `MemoryReservation`. Temporary allocations and steady-state build metrics have distinct lifetimes. [Matches](https://github.com/apache/datafusion/blob/2f6c665fef63936f08a4aa7a4fb01b87a4d2b009/datafusion/physical-plan/src/joins/join_index/matches.rs), [processor](https://github.com/apache/datafusion/blob/2f6c665fef63936f08a4aa7a4fb01b87a4d2b009/datafusion/physical-plan/src/joins/hash_join/batched_join_processor.rs).

For standard equality, NULL join keys are masked out. The dense selection rejects NULL-containing inputs when NULLs compare equal. The dense implementation nevertheless contains a NULL handle, which the reviewer identifies as unreachable through this selection path. A proposed test matrix should distinguish SQL-visible NULL semantics from internal directory behavior and exercise the 64-bit implementation on small fixtures through an internal API.

## Relation to prior work

The historical ExactCSR/HashCSR adapter chose layout using a coarse admission gate, with build and estimated probe sizes, sampled multiplicity and optional payload reorder. B constructs the distinct-key directory and gathers duplicate metadata during insertion, followed by final scatter. It avoids the historical admission policy and payload reorganization. Because B shifts exact equality to the build for the general path and avoids pointer chasing per probe match, the cost change depends on build size, repeats, probe hits and payload gathers.

Matt's experimental dense patch counts slot frequencies, assigns group ranges, and scans keys again to scatter row IDs in build order. Singleton keys retain inline handles. The patch bypasses the pending-pair builder for dense keys. It was proposed after B, and tests and x86 measurements are separate from the A/B campaign. The Apple M5 Max numbers and sampled build CPU in the review are external evidence. [Counting-sort review](https://github.com/apache/datafusion/pull/27746#discussion_r4698342517).

The architecture follows the upstream plan in [#27398](https://github.com/apache/datafusion/issues/27398) after the regular-join refactor. [#17494](https://github.com/apache/datafusion/issues/17494) illustrates chain traversal on a TPC-DS Q72 shape. [#27530](https://github.com/apache/datafusion/pull/27530) and [#26447](https://github.com/apache/datafusion/pull/26447) are closed chain-grouping proposals. [#27614](https://github.com/apache/datafusion/issues/27614) identifies the hot-group case amid unique keys, covered by Q28 in [#27528](https://github.com/apache/datafusion/pull/27528). Review items concern whole-build hashing, up-front group capacity, general equality cost, dense counting sort, dense NULL reachability and missing branch-level tests. The published research contributes workload evidence and a precedent for the evaluated dense approach. [Full review](https://github.com/apache/datafusion/pull/27746#pullrequestreview-6061888053).
